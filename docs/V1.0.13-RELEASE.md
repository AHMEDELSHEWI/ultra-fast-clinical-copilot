# V1.0.13 — Clinical workflow integrity candidate

**Decision: engineering candidate only. Patient care: NO_GO. Synthetic data only.**

This is an incremental continuation of AHMEDELSHEWI/ultra-fast-clinical-copilot at commit `778d44bc8305ff288737254e2958b4b370451fa8`, not a new application or an approved clinical release. Original versioned files and the main entry point remain unchanged. The supplied MASTER PROMPT V5 attachment could not be read in this session; its full requirements have not been re-certified. The existing repository and the user's confirmed ten-section documentation requirements were the implementation inputs.

## Implemented

The build applies the shared V1.0.8 schema corrections inherited by the V1.0.12 loader chain at build time. It replaces recursive runtime HTML loading with one self-contained artifact. V6/V7 patient age, gestation and status UX is preserved; its mutation observers are replaced with explicit render lifecycle events. Unvalidated likelihood ranking and legacy voice activation are quarantined rather than represented as tested AI.

A six-phase command center records five typed safety answers in the existing encounter store, preserves positive safety findings, and merges the review lists from every active clinician-confirmed complaint. Review actions are functional, audited, idempotent, and invalidated when the clinical context changes. Keeping a review item creates neither a diagnosis nor an order. Content remains the inherited starter pack, not newly validated guideline content.

The documentation generator uses exactly these sections: Chief Complaints; History of Present Illness; Past History; Physical Examination; General Examination; Latest Vital Signs; Local Examination; Primary Diagnosis; Secondary Diagnosis; Management and Plan. Confirmed recorded facts are used. Missing facts remain Not documented. Primary diagnosis requires explicit designation. Investigation names are plain, with separately recorded results and patient-specific medical reasoning. Medication fields are conditional and canonically ordered; unverified medication records are excluded from the active note and flagged. Recording a medication does not establish administration. A legacy Done procedure does not establish performance.

Finalized notes preserve their original content. Common clinical edits and restoration over a finalized encounter are blocked; late entries are separately timestamped addenda with reasons. This is a local application-level integrity control, not an authenticated or tamper-proof medical record system. Exported files can be edited outside the application.

## Reproduce

Use Node 22:

```sh
node scripts/build-v1.0.13.cjs
node --test tests/v1.0.13*.test.cjs
```

The built app is `dist/v1.0.13/ULTRA_FAST_CLINICAL_COPILOT_V1.0.13.html`.

Optional browser tests require Python and Playwright with Chromium:

```sh
python tests/v1.0.13-browser.py
```

The browser harness injects the generated HTML into an isolated page. It does not simulate a real origin, an installed application, patient data, an authenticated EHR, or durable storage. It uses a clipboard mock to test COPY ALL payload, not operating-system clipboard permissions.

## Not implemented or not established

There is no connected generative model, streaming transcription, speaker diarization, grounded clinical RAG, clinically validated differential ranking, autonomous prescribing, live EHR read/write, authenticated multi-user backend, institution-grade access control or regulatory approval in this candidate. Legacy source code is not proof of a delivered capability. No claim of HIPAA/PDPL compliance, guaranteed insurance coverage or complete medicolegal protection is made.

The prior main-branch V1.0.8 integrity workflow was already failing. This candidate adds independent V1.0.13 validation; it does not claim to have repaired or deployed the historical main branch. A successful engineering pipeline does not change the clinical NO_GO decision.

## Sully comparison: no head-to-head claim

Sully's own public documentation describes ambient capture, clinical-note drafting, clinician approval, EHR writeback, local capture with later sync, and Arabic support. These are vendor-described capabilities, not independently tested by this project. Arabic, offline behavior and human approval alone are therefore not defensible claims of unique superiority.

Sources reviewed 7 October 2026:

- https://www.sully.ai/agents/scribe
- https://www.sully.ai/help-center/articles/what-languages-does-sully-ai-support
- https://www.sully.ai/help-center/articles/how-does-the-ai-scribe-convert-conversations-into-clinical-notes

The appropriate next competitive scope is a validated emergency-care workflow: provenance-backed extraction, multi-complaint reasoning, temporal reassessment, reliable pediatric/renal/weight handling, and fast, verified documentation. All comparisons must use the same consented or synthetic cases and blinded clinician review. “A million times better” is not a measurable product specification.

## Next acceptance gates

1. A real-origin browser/device test matrix, storage/recovery verification, and a reviewed versioned clinical-content registry. Do not activate placeholder guideline or medication content.
2. A genuine model/voice adapter with explicit data-flow consent, source-span provenance, negation/temporality checks, uncertainty, deterministic calculation boundaries, and recorded evaluation results. Disconnected adapters must remain visibly disconnected.
3. Authenticated server-side event storage, RBAC, audit integrity, migration/backup tests and an institution-approved EHR test environment. No live patient writes or prescriptions without explicit clinician authorization.
4. Blinded evaluation against the same tasks in Sully: unsupported facts per note, critical omissions, correction count, missed deterioration, review time, latency distribution and cost per encounter. Predefine thresholds with clinical owners; no inferred superiority from marketing percentages.
